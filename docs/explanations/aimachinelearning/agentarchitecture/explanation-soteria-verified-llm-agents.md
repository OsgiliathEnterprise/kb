# Soteria: Formally Verified Planning with Runtime Enforcement for Safe LLM Agents

> Corrected 2026-11-16 by KB Zookeeper: the first intake version invented component names ("PRAISM", "SafePilot") and a threat taxonomy not present in the paper. Core attribution (Princeton, Sharad Malik, NeurIPS'26 Oral) was right; details replaced with facts verified against the arXiv abstract page.

## Overview

Soteria (Mike He, Ankush Desai, Sharad Malik, Aarti Gupta — Princeton; arXiv:2611.17880, 13 Nov 2026, cs.AI, **accepted as NeurIPS 2026 Oral**) reconciles the two objectives of tool-calling LLM agents — **utility** (complete the task) and **safety** (conform to domain policies/correctness constraints) — through **verified hierarchical planning plus runtime enforcement of specifications**. Their tension: blocking an unsafe action prevents a violation but strands the agent with no principled recovery; existing approaches sacrifice one objective for the other.

## Problem Statement

Agents executing multi-step tool calls need guarantees that guardrails/alignment bolt-ons do not provide, while remaining capable. Enforcement alone blocks but does not guide; verification alone cannot cover dynamic environment states.

## Key Contribution

- **Pre-execution**: the agent generates a structured hierarchical plan that is **formally verified against the specifications before any tool invocation**.
- **During execution**: the verified plan plays a **dual role** — keeping the agent on specification-conformant trajectories, and **providing recovery guidance when unsafe actions are blocked** (so blocking doesn't strand the agent).
- **Utility is untouched by design**: the underlying LLM is unconstrained; safety lives in the plan-verification + enforcement layer.

## Technical Approach

Plans are generated by the LLM but verified symbolically before execution; the runtime enforcer mediates actions against the same specs. Because a verified plan already encodes a safe path to the goal, a blocked action triggers replanning guidance from the plan structure rather than a dead end — this is what breaks the safety–utility trade-off.

## Results

Across multiple benchmarks covering diverse tool-use tasks: **1.7× the average task success rate of the best baselines, with no policy-specification violations** — evidence that safety and utility need not be traded off.

## Relevance to Our Domain

The "secure by construction" counterpart to our attack-side agent-security notes. For platform teams the verify-then-enforce pattern maps onto policy engines (OPA-style admission control) already used in Kubernetes/DevSecOps stacks; the plan-guided-recovery idea is worth stealing for any tool-call guardrail implementation.
