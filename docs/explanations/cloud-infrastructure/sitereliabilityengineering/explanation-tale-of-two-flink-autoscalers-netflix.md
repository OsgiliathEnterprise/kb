# A Tale of Two Flink Autoscalers: Netflix's In-House vs OSS Autoscaler

## The Setup

Netflix has run stream processing on Apache Flink since 2017 and operates **30,000+ Flink jobs** across multiple AWS regions as of 2026 — most generated by their managed platform Data Mesh. A scaling action is expensive: by default it means **taking a savepoint, stopping the job gracefully, and restarting it at the new size** — minutes for large stateful jobs. The problem: give each job the resources it needs, when it needs them, without a human in the loop.

## Autoscaler #1: Watching From Outside (built ~2019)

An in-house autoscaler shaped like a **stream-processing job**: ran on Mantis, consuming a live feed of **cluster-level metrics from Atlas** (CPU, network, Kafka lag, input-rate, consume-rate for every job). Combined lag-derived catch-up time, CPU/network thresholds, observed performance history, and regression over recent input rate to decide scaling.

- Operates **independently of the Flink platform** — unaffected by issues within Flink itself
- Built as a streaming job → easy to scale; each autoscaler node handled a subset of jobs, no custom sharding logic
- **Cut resource usage 25–45%** across thousands of managed pipelines

**Its ceiling:** reasoned about whole clusters through coarse container metrics and scaled a **single knob — total TaskManager count**, so every operator moved together. Fit simple single-operator pipelines; couldn't reason about multi-operator stateful DAGs. And the autoscaler is only as good as the metrics beneath it: a networking migration quietly broke some Atlas metric reporting, and the gap stayed invisible until it surfaced in production much later.

## Autoscaler #2: Reasoning From Inside (OSS)

The [Apache Flink Autoscaler](https://nightlies.apache.org/flink/flink-kubernetes-operator-docs-main/docs/custom-resource/autoscaler/) estimates each operator's **true processing rate (TPR)**: Flink reports per-subtask the fraction of each second spent doing actual work (vs backpressured/idle). Dividing observed throughput by that busy fraction extrapolates capacity:

```
an operator handling 700 records/sec while busy 70% of the time
has TPR = 700 / 0.7 = 1,000 records/sec
```

Starting from the sources, it **walks the job graph** and uses each operator's TPR, input/output ratios, and a target utilization to compute the **parallelism every vertex needs** so no operator becomes the bottleneck — rather than resizing the whole cluster as a unit. Decisive difference: it can scale exactly the **stateful, multi-operator jobs** the homegrown system couldn't, and each job carries its own configuration (stabilization periods, thresholds).

## Making It Work at Netflix Scale

Adopting the *algorithm* was easy (community did the hard part); running it across 30k jobs was the work:

1. **Standalone library, not operator-locked.** The OSS core was refactored into four generic interfaces — context (job metadata + REST info), state store, event handler, and a **realizer** that applies decisions — letting Netflix plug it into their own control plane (their Flink platform doesn't use the community K8s operator).
2. **Spring Boot + Temporal orchestration.** An orchestrator workflow polls the Flink control plane ~once a minute and starts **one long-running durable workflow per job**. Each per-job workflow pulls per-vertex metrics from the JobManager, runs the evaluation, and hands decisions to the realizer. *Workflow-per-job* was a direct response to pain: a single batch loop over all jobs was fragile — one slow job stalled everything behind it. Isolated blast radius now.
3. **Three engineering gaps** (in their internal Flink fork, some contributed upstream, e.g. [FLINK-36172](https://issues.apache.org/jira/browse/FLINK-36172)):
   - **Metric collection at high parallelism** — JobManager changed to cache transient metric names + server-side filtering → works on jobs up to **3,000 subtasks** (previously struggled above ~1,000)
   - **Forward chaining** — two vertices joined by a *forward* connection must run at the same parallelism (in-memory handoff on a fixed local channel); scaling one alone silently converts the edge into a network shuffle. Their fork detects forward-connected subgraphs and scales each as a unit.
   - **Sink limits** — async-sink backpressure detection so the scaler doesn't scale into a sink that can't absorb more.
4. **Safety checks before actuation** — refuses to scale down during a regional failover evacuation; verifies enough disk for the new cluster's checkpoint state; adds a standby buffer for larger clusters.

## Results and the Eager-Scale-Down Trap

- GA for custom jobs; one client telemetry/logging team cut annualized Flink compute spend **58% (~$1.1M/year)** — driven by adapting to daily cycles, continual adjustment after performance improvements, and uniform container dimensions enabling better bin-packing.
- **Scaling down too eagerly is its own trap:** cut too deep → CPU saturates, lag spikes, and the system can't react instantly because its metric window and stabilization period must rebuild after each restart. Netflix runs **target utilization 0.45, below the community default of 0.7** — deliberately trading a little efficiency for stability.
- **The remaining bottleneck is state recovery, not the scaler.** Fast rescaling depends on Flink Core's state restoration; Flink 2's [disaggregated state](https://nightlies.apache.org/flink/flink-docs-master/docs/ops/state/disaggregated_state/) (state in external storage) is what they're experimenting with to break that bottleneck.

## Three General Lessons

1. **Metric choice matters more than algorithm sophistication.** The most useful debugging was never the scaling math — it was which signal to trust. Understand your metrics before tuning the algorithm.
2. **Set sensible defaults, but leave room to tune.** One good default covers most jobs (the point of a platform), but per-job overrides prevent punishing the outliers — and hide the knobs that need deep expertise.
3. **Adopt, then extend.** When a strong community project appeared: neither defend the in-house investment forever nor rip it out overnight — adopt for new workloads, contribute fixes back, plan a deliberate migration.
