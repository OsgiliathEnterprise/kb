Making Big Downloads Resumable in Firefox: The network.http.response.timeout Fix

Goal​

Get Firefox to actually resume interrupted large downloads (and make them a bit more stable in general), when the server supports resumable transfers.

Background​

Firefox 28 and newer — i.e. every modern version since ~2014 (see the original 2014 note on network.http.response.timeout) — ships with network.http.response.timeout set to 300 seconds. That default is still current on firefox-main: modules/libpref/init/all.js sets pref("network.http.response.timeout", 300); (searchfox, line 1131). This interferes with resuming big downloads and with their general stability: when a long transfer exceeds the timeout, the browser's handling of the failure appears to interfere with its ability to resume what it already downloaded.

Upstream history. The pref's behavior with long-lived connections was upstream bug 1024015 ("network.http.response.timeout breaks applications with long lived http connections", 2014, RESOLVED FIXED in Firefox 31–33): the fix made the response timeout apply only when TCP keepalives are disabled for HTTP — so on modern Firefox the effective timeout semantics also depend on keepalive state. A related bug, 1060202 ("HTTP Response timeout not working as configured in Firefox", RESOLVED WORKSFORME), documents that the pref did not always behave as its name suggests — another reason to verify the observable behavior rather than trust the setting alone.

Sibling timeout prefs. network.http.response.timeout is one of several network timeout knobs in about:config; knowing the others prevents misdiagnosis when long transfers time out:

network.http.connection-retry-timeout250 sHow long a request may wait for a free connection

Steps​

  1. Open about:config in Firefox and accept the warning.
  2. Find network.http.response.timeout (type is int).
  3. Set it to 0 (disabled) or a very large value.
  4. Verify on a large file from a server that supports Range requests: interrupt the download, then resume — the existing .part file should be used instead of starting over.

Prerequisites and Caveats​

  • The server must support resumable downloads (HTTP Range requests). No Firefox setting helps if the server can't resume.
  • The exact mechanism is not fully understood. Experimentally, Firefox appears to rely on connection timeouts rather than the .part files it downloads when resuming: without the timeout change, Firefox will happily ignore an existing .part file and start over. The author could not locate the responsible code in Firefox's source.
  • Firefox also appears to do hidden retries before declaring a download failed, and exceeding network.http.response.timeout interferes with that retry process — disabling the timeout appears to let the retries (and thus resumption) work.
  • Resumable downloads in Firefox are unstable in general — a known problem in some form since at least 2005. There is even a manual .part shuffle workaround to force Firefox to resume; this howto's setting-based fix avoids that.

Non-Firefox Fallback​

When the server supports resumption, wget is a stable alternative:

wget -c -O "$filename" "$url"

wget -c (continue) is fairly stable overall and is the recommended escape hatch for unreliable browser-based resumption.

Manual .part Backup and Add-on Alternatives​

  • Backup the .part before restarting Firefox. The official Mozilla Support procedure for resuming an interrupted download is: back up the .part file before starting Firefox, then let Firefox see the existing partial file. Firefox keeps two files during a download — the final filename (empty until completion) and the .part working file — so the .part is what actually carries the already-downloaded bytes (Super User).
  • Add-on alternatives. If the setting-based fix isn't enough, two add-ons automate resumption: Restart Interrupted Downloads (automatically resumes interrupted downloads) and Download Auto Resumer (retries downloads that failed with NETWORK_FAILED). These complement rather than replace the network.http.response.timeout change — the add-on restarts the transfer, the pref change stops Firefox from tearing down the transfer in the first place.

Verification​

After the change, the observable behavior is: interrupt a long download (network drop or manual cancel), then resume — the transfer continues from the .part offset instead of restarting at byte 0. If it still restarts, check that the server actually returns 206 Partial Content for Range requests (e.g. with curl -r 0-100 -I <url>).
