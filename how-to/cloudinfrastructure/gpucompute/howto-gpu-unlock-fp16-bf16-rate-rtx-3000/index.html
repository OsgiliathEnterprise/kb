How to Unlock the FP/BF16 Issue Rate on RTX 3000 Series Cards (gpu-unlock)

Consumer GeForce Ampere cards (GA102/GA103/GA104/GA106) run FP16/BF16 FMA instruction issue at half the rate of the identical professional workstation dies (e.g. RTX A5000 vs RTX 3090). gpu-unlock (v1.0.0, ~4.1k stars) is an open-source Linux kernel module that removes the restriction at boot, without patching the NVIDIA driver or flashing firmware — so it survives driver updates without manual re-patching.

Effect: doubles the instruction issuing speed of FP/BF16 FMA into FP32 operations. Reported GEMM results on a 3090 Ti (dense 8192³, 450 W, five sample medians, FP32 accumulation):

InputBeforeAfter
FP1687.46 TFLOPS118.39 TFLOPS
BF1687.50 TFLOPS157.41 TFLOPS
TF3242.58 TFLOPS82.61 TFLOPS

Matrix-heavy work speeds up (LLM prefill +14–36% across several reports, plus diffusion and FlashAttention). LLM decode (memory-bandwidth-bound) and INT8 work stay about the same; reports comparing outputs found them bit-identical before and after.

How it works​

The module combines the CMP unlocker's V67/PLM technique with the pre-driver timing of the UEFI approach. During early initramfs boot, before the unmodified nvidia driver binds the card, it:

  1. clears bus mastering that board firmware may have left on (e.g. Supermicro X11 does this regardless of option ROM settings),
  2. writes the speed selectors — SS0 = 0x88888888 (full BF16 rate) and the 4-bit SS1 = 0x8 (IMLA4),
  3. performs FLR (function-level reset).

It is neither a UEFI application nor a patched NVIDIA driver. Cards already bound to a driver or powered down are skipped; loading the module by hand after nvidia bound a card does nothing.

Install​

git clone https://github.com/Zagitta/gpu-unlock
cd gpu-unlock
make install

make install detects the distribution via /etc/os-release (ID, then ID_LIKE) and selects the right installer; explicit targets also exist: make install-arch (makepkg), make install-deb, make install-rpm (DNF required). Every build downloads pinned NVIDIA/CachyOS inputs over HTTPS, checks their SHA-256, and generates firmware only in the build directory and binary packages (cached in ~/.cache/gpu-unlock/inputs).

Opt-in: kernel command line​

Append gpu_unlock.targets=... to the kernel command line, keeping existing options:

gpu_unlock.targets=all                                # every unbound GA10x card
gpu_unlock.targets=0000:21:00.0                       # only this card
gpu_unlock.targets=0000:21:00.0,0000:22:00.0         # comma-separated

Addresses are full PCI names as lspci -D prints them. Per-distro:

  • GRUB (Debian/Ubuntu/Mint): inside GRUB_CMDLINE_LINUX_DEFAULT in /etc/default/grub, then sudo update-grub
  • GRUB (Arch/CachyOS): same edit, then sudo grub-mkconfig -o /boot/grub/grub.cfg
  • Fedora/RHEL: sudo grubby --update-kernel=ALL --args="gpu_unlock.targets=all"
  • systemd-boot: append to the options line of your boot entry (bootctl status shows its location)
  • UKI / generated entries: add to /etc/kernel/cmdline and regenerate boot images (e.g. sudo mkinitcpio -P)

The packages put gpu_unlock and its firmware in the initramfs and load it there, before nvidia can bind a card (mkinitcpio drop-in /etc/mkinitcpio.conf.d/zz-gpu-unlock.conf inserts gpu_unlock right before nvidia in MODULES; initramfs-tools and dracut have their own drop-ins). There is deliberately no softdep nvidia pre: rule — kmod honours only the first one it reads and other packages' rules would silently override it.

Boot sequence​

Suspend/resume behavior​

Suspend to RAM powers the cards off, which resets the speed selectors. After resume, the module re-unlocks every card it unlocked at boot before nvidia resumes it (its suspend notifier runs just ahead of NVIDIA's; NVreg_UseKernelSuspendNotifiers=1 is the default), adding ~1 second to resume. A card that kept power (suspend to idle) is only re-read. Disable with gpu_unlock.resume=0 on the kernel command line (or write 0 to /sys/module/gpu_unlock/parameters/resume). Hibernation is not covered. If a card's firmware never stops, the module logs it and keeps the DMA buffers until the next power off.

Verify​

journalctl -k -b | grep gpu_unlock
lspci -nnk -s 0000:21:00.0

To stop unlocking: remove gpu_unlock.targets= from the kernel command line (deleting it in the bootloader's edit screen works for a one-off boot). Removing the packages removes the module and the initramfs drop-ins.

Reports also cover up to four cards in one machine, the display card (its firmware framebuffer keeps running; screen is blank from the reset until nvidia-drm takes over), and cards passed through to a VM with vfio-pci.

Independent cross-check​

A separate Medium write-up (142 TFLOPS in a 3090 Ti) describes the same mechanism as an artificial register lock inside consumer GA102 chips and reports +48.4% dense BF16 GEMM on a 3090 — consistent with the repo's own numbers within benchmark methodology differences.

Related unlock project for Ada (RTX 40 series), verified 2026-10-26​

gpu-unlock-ada (JustAResearcher) applies the same pre-driver technique to Ada Lovelace cards: on an RTX 4090, FP16 with FP32 accumulation went from 165.6 to 331.6 TFLOPS and BF16 from 165.5 to 330.6 TFLOPS; an experimental RTX 4070 Ti SUPER target (single card, 240 W cap) doubled from 95.0 to 189.9 TFLOPS in FP16. INT8 and FP8 did not move, consistent with only the FP32-accumulate path ever being throttled. Caveats from its README: the first attempt needs a full power-off (not a warm reboot), boot entries must be re-checked after every kernel upgrade, and multi-GPU setups and display handoff are unvalidated. A community ComfyUI run on a 3090 Ti cut a BF16 image-generation job from 72 s to 45 s. TechPowerUp rounded up both projects ("Modders unlock NVIDIA GeForce RTX 20/30/40 series compute limits").

Caveats​

  • The module is GPL-2.0-only; the generated payload derives from the pinned CMP reference (NVIDIA firmware remains under its own terms — see firmware/NOTICE.md and licenses/).
  • The 3080 Ti OEM variant shows the unlock completing but BF16 staying at half rate — verify on your specific card.
  • This is a workaround for factory-imposed rate limiting; treat it as a performance hack, not a supported configuration.
