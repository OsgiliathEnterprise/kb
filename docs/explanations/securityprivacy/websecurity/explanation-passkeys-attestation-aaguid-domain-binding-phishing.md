# Passkeys Are Not a Trap — What Attestation Actually Does, Domain Binding, and Why TOTP Is the Regression

A viral post argued that passkeys are a security trap: they are bound to the origin that created them, so they can be stolen and replayed, and "you should have used TOTP instead." Scott Helme's reply (and the evidence he assembles) shows the claim inverts the actual threat model. This note explains what passkey attestation does and does *not* do, why the origin binding is a feature against the right threat, and where the real trade-offs are.

## What the "trap" argument actually says

The argument runs roughly: a passkey is bound to the domain that created it; therefore if an attacker gets a copy of the passkey (e.g. via a compromised device or a malicious app), they can use it on that same domain, so passkeys are no better than a secret that can be replayed — and a TOTP code, being short-lived, would have been safer.

Three things are wrong with this, in increasing order.

## What attestation actually is (and is not)

When a passkey is created, the authenticator (platform device or security key) can provide **attestation**: a signed statement that the credential was generated by an authenticator of a certain class, identified by an **AAGUID** (attestation GUID). The server can verify this and see, for example, "created on an iPhone" or "created by YubiKey 5".

The critical properties:

- Attestation is **a property of the authenticator, not of the origin**. It tells you *who made the key*, not *where the key can be used*. The "bound to the domain" part of the viral claim conflates two different bindings:
  - **Origin binding** (WebAuthn `credentialId` scope): the credential is only valid for the `rpId`/origin that created it. This is a *feature* — it is exactly what stops a stolen passkey from being portable across sites, unlike a password.
  - **Attestation**: the metadata about the authenticator's class. It is evidence you can use in risk decisions (a platform passkey created on a device you recognise vs. an unknown AAGUID), not a portability restriction.
- Attestation is **best-effort and often absent**: many authenticators (especially platform ones in privacy mode) return *none* or *basic* attestation, in which case you get no cryptographic statement about the key's origin — only the AAGUID, which is self-asserted metadata. So the design of your risk system must not *depend* on strong attestation being present.
- The AAGUID is **not a security boundary**. It is a hint. A malicious app can create a passkey with a plausible-looking AAGUID; the cryptographic protection is in the private key never leaving the authenticator and the challenge-response protocol, not in the AAGUID value.

## Why the origin binding is the feature, not the trap

The replay argument — "a stolen passkey can be replayed on the same domain" — is true, but it is a *weaker* threat than the alternatives:

- **Against phishing**: a passkey cannot be phished the way a password or a TOTP code can be. WebAuthn's **domain binding** means the browser only offers a credential when the *user's browser* is genuinely on `example.com` — a lookalike site (`exampl3.com`) gets nothing, because the `rpId` does not match. TOTP codes, by contrast, are exactly what a phisher wants: the user on a convincing fake page is asked to "verify" and types a six-digit code straight into the attacker's box. The code is origin-agnostic, so it is *portable to the phisher*; the passkey is not.
- **Against keyloggers**: a passkey never appears on screen and is never entered, so there is no secret for a keylogger to capture.
- **The honest residual risk** — a compromised *device* (malware that controls the authenticator directly) — exists for TOTP stored on the same device too, and for passwords in the same browser. It is not unique to passkeys, and it is a device-security problem, not a protocol problem.

So the correct comparison is: passkeys are resistant to the *common* attack paths (phishing, credential stuffing, keylogging) precisely because of the binding the viral post calls a trap, at the cost of a device-compromise residual risk that the alternatives share.

## Where the real trade-offs are

- **Recovery is the weak end.** A lost device with a platform-only passkey can be a lockout if you have no backup passkey on another device or no fallback factor. The mitigation is design-level: always register a second passkey on a different device, and keep one out-of-band fallback. This is a process cost, not a protocol flaw — and it is the same cost as any multi-factor recovery design.
- **Attestation strength varies by platform and mode.** If your risk model needs to distinguish "device I own" from "unknown authenticator", treat "no attestation" as the default case, not the exception, and use AAGUID as a signal, never a gate.
- **Sync (platform passkeys via cloud sync) extends the trust boundary** to the sync provider. Some organisations restrict platform passkeys for exactly this reason; FIDO2 security keys sidestep it. The choice is a policy decision with a real, bounded cost — still smaller than phishing exposure.
- **TOTP is not the safe fallback it is presented as.** TOTP is a *factor*, not a *credential*: it does not authenticate the user to the origin (you still need something to log in with first), it is fully portable to any phisher, and it is silent about where the code was generated. Replacing passkeys with TOTP to "avoid the trap" is replacing a phishing-resistant credential with a phishing-capturable code.

## Key takeaways

- **Origin binding is the feature**: it is what makes passkeys un-phishable and non-portable to attackers, the exact opposite of the viral claim's framing.
- **Attestation tells you who made the key, not where it can be used** — and it is often absent, so risk systems must treat "no attestation" as normal.
- **The residual risk is device compromise**, which TOTP and passwords share; it is not a passkey-specific trap.
- **The real design work is recovery and policy**: second passkey on another device, out-of-band fallback, and an explicit stance on sync vs. hardware keys.
- **TOTP as "safer" inverts the threat model**: it is portable to phishers and does not authenticate the user to the origin.
